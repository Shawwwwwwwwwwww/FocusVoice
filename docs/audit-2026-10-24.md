## 0. 结论摘要（先看这一段）

用户三条痛点都能在代码里找到直接对应的语句，且不是"玄学"：

| 痛点 | 直接根因（一句话） | 关键行 |
|---|---|---|
| ① 点击鼠标之后经常无法触发 | 长按判定依赖 **主队列延时 + mouseUp 无条件取消**，且判定前的 AX 命中查询在**主线程同步、无超时、失败裸 return**；再加上 42pt/AXToolbar 黑名单误杀、全程零反馈 | 1779, 1807-1813, 1819-1832, 1828-1829, 398-408, 345 |
| ② whisper 要等 2-3 秒，想边录边看字 | 冷启动/每次错误都会重启 `whisper-server`；没有预热、没有部分结果；而"腾讯云实时流"因 **PCM 回调从未触发**（`int16ChannelData` 恒 nil）+ **默认引擎名在实时接口不合法** + **签名未 URL 编码**，实际几乎不可用 | 517/634, 989, 963-966, 170, 925-928 |
| ③ 更清亮/更快/更可靠 | 单文件 3404 行、状态全靠 4 个布尔 + UUID 比较、主线程承担 AX/音频转换/文件 IO/AppleScript、错误全部静默、设置项存在死代码（`keepClipboard`、`setEnabled`） | 1897-2228, 1432-1454, 150-152, 1793 |

**最危险的三段代码**（建议优先重构）：
1. `MouseHoldWatcher.checkHold()`（1819-1832）——无超时 AX 同步查询 + 5 处裸 `return`。
2. `TextInsertion.insert()`（1410-1455）——AX 不校验 + 三路粘贴无条件全发 + 剪贴板永久覆盖。
3. `BuiltInMicRecorder.captureOutput()`（474-523）/ `SystemAudioRecorder.stream()`（590-640）——`int16ChannelData` 恒 nil，实时流 0 字节；转换缓冲容量截断导致丢采样。

## 2. P0（直接导致"点了没反应"、崩溃或丢字）

### P0-1 长按判定依赖主队列延时，mouseUp 无条件取消 → 主线程一卡就整次丢失

- **位置**：`MouseHoldWatcher.start()` 1786-1790；`handle` 1807-1813；`checkHold` 1819-1832；`cancelPending` 1834-1838。
- **代码**：
  ```swift
  monitor = NSEvent.addGlobalMonitorForEvents(matching: [.leftMouseDown, .leftMouseUp]) { [weak self] event in
      let type = event.type
      let point = NSEvent.mouseLocation            // 1788
      Task { @MainActor in self?.handle(type: type, point: point) }   // 1789
  }
  ...
  let work = DispatchWorkItem { [weak self] in
      Task { @MainActor in self?.checkHold() }      // 1808
  }
  holdWork = work
  DispatchQueue.main.asyncAfter(deadline: .now() + holdDelay, execute: work)  // 1811
  ...
  case .leftMouseUp:
      cancelPending()                               // 1813 无条件取消
  ```
- **现象**：按满 1.2 秒仍然不弹 HUD；或者松手之后 HUD 才延迟出现。
- **根因**：判定条件不是事件时间戳，而是"**mouseDown 回调被主线程执行的那一刻** 起算 1.2s"。主线程一旦阻塞，down/up 回调被一起补跑：down 注册定时器，紧接着 up 取消它。全局鼠标监听在主线程递送，app 自身任何同步工作都会造成这个窗口。真正的阻塞源在本文件里就有：`SystemAudioRecorder.stop()` 572-577（主线程 `sem.wait(timeout: 2)`）、`TextInsertion.insert()` 1432-1453（主线程 `usleep`×3 + `NSAppleScript`）、`Recognizer.tencentCloud` 1229-1245（主线程 `Data(contentsOf:)` + base64 + JSON）、`WhisperServer.request` 1059（主线程读整段 WAV）、`BuiltInMicRecorder.start` 456（主线程 `startRunning`）、`AX.*` 全部同步 IPC。
- **条件**：用户在上一次录音结束后的 0-1s 内再次长按（最自然的"连续听写"动作），几乎必踩。
- **修法（推荐：事件时间戳判定 + 定时器只做蓄力视觉）**：
  ```swift
  @MainActor final class MouseHoldWatcher {
      private var monitor: Any?
      private var downAt: CGPoint?
      private var downTimestamp: TimeInterval = 0
      private var holdWork: DispatchWorkItem?
      private let holdDelay: TimeInterval = 0.6          // 与新的蓄力环一致
      private let moveTolerance: CGFloat = 6
      var onArm: ((CGPoint?) -> Void)?                   // 按下即亮环 / 取消熄灭
      var onHold: ((CGPoint) -> Void)?

      func start() {
          monitor = NSEvent.addGlobalMonitorForEvents(
              matching: [.leftMouseDown, .leftMouseDragged, .leftMouseUp]
          ) { [weak self] event in
              // 回调里只记录，绝不做 AX / 磁盘 / 网络
              let p = NSEvent.mouseLocation
              guard let self else { return }
              MainActor.assumeIsolated { self.handle(event, at: p) }
          }
      }

      private func handle(_ event: NSEvent, at p: CGPoint) {
          switch event.type {
          case .leftMouseDown:
              guard enabled, isPointInsideHUD?(p) != true else { return }
              downAt = p
              downTimestamp = event.timestamp          // ← 用事件戳，不用墙钟
              onArm?(p)
              scheduleHoldTimer()
          case .leftMouseDragged:
              guard let d = downAt else { return }
              if hypot(p.x - d.x, p.y - d.y) > moveTolerance { disarm() }
          case .leftMouseUp:
              defer { disarm() }
              guard let d = downAt else { return }
              let held = event.timestamp - downTimestamp
              // 已按满但定时器被主线程拖晚：用时间戳补偿触发一次
              if held >= holdDelay,
                 hypot(p.x - d.x, p.y - d.y) <= moveTolerance,
                 holdWork != nil {
                  holdWork = nil
                  onHold?(d)                            // 用按下点，而不是松开点
              }
          default: break
          }
      }

      private func scheduleHoldTimer() {
          holdWork?.cancel()
          let w = DispatchWorkItem { [weak self] in
              MainActor.assumeIsolated { self?.fireIfStillPressed() }
          }
          holdWork = w
          DispatchQueue.main.asyncAfter(deadline: .now() + holdDelay, execute: w)
      }

      private func fireIfStillPressed() {
          guard let d = downAt else { return }
          // 双保险：mouseUp 若丢失，只有在物理按键仍按下时才触发
          guard NSEvent.pressedMouseButtons & 0x1 == 1 else { return disarm() }
          let cur = NSEvent.mouseLocation
          guard hypot(cur.x - d.x, cur.y - d.y) <= moveTolerance else { return disarm() }
          holdWork = nil
          downAt = nil                                  // 防止 mouseUp 补触发
          onHold?(d)
      }

      private func disarm() {
          holdWork?.cancel(); holdWork = nil; downAt = nil; onArm?(nil)
      }
  }
  ```
  > 关键点：mouseUp 只用于"不到阈值就取消"，**不再无条件取消**；定时器触发前检查 `pressedMouseButtons`；真正的触发点用 `event.timestamp`，主线程再忙也不会把"按满 0.6s"误判成短按。

- **验收**：在注入路径人为 `usleep(300_000)` 制造主线程阻塞，连续 20 次长按仍应 20 次触发；日志记录 `held` 值。

### P0-2 AX 命中/判定全部在主线程同步执行、无超时、失败静默

- **位置**：`checkHold` 1828-1829；`AX.element(atAppKitPoint:)` 310-316；`AX.isEditable` 271-298；`InputDetector.isInputTarget` 337-414（其中 366-377 祖先回溯最多 30 层 × 每层 2 次同步 AX IPC）。
- **代码**：
  ```swift
  guard let hit = AX.element(atAppKitPoint: start) else { return }          // 1828 静默
  guard InputDetector.isInputTarget(atAppKitPoint: start, hit: hit) else { return }  // 1829 静默
  ...
  guard AXUIElementCopyElementAtPosition(system, Float(cgP.x), Float(cgP.y), &element) == .success else { return nil } // 314
  ...
  for _ in 0..<30 {                                                        // 366
      if let p = AX.element(AX.value(cur, kAXParentAttribute)) { ... }     // 367-368
  }
  ```
- **现象**：在微信/Codex/Chrome 里长按，有时完全没反应（无 HUD、无菜单提示）；有时要等 1-3 秒才出 HUD；经常一次成功一次失败。
- **根因**：
  1. `AXUIElementCopyElementAtPosition` 是**同步 IPC**，默认对目标 app 的 messaging timeout 约 6 秒，本文件 **从未调用 `AXUIElementSetMessagingTimeout`**（全文件 grep 为 0）。
  2. Chromium/Electron 的 AX 树默认不建，客户端首次查询时由渲染进程现建；这段时间查询会慢/返回 `kAXErrorCannotComplete`（-25204）。
  3. 失败用裸 `return`：无日志、无 HUD、无重试。用户无法区分"没权限 / 不是输入框 / AX 超时 / 移动超限"。
  4. 这些调用都在主线程，直接制造 P0-1 的阻塞条件，形成"越点越卡、越卡越点不出来"的正反馈。
- **条件**：Electron/Chromium 应用（微信新版、Codex/ChatGPT、Chrome/Safari 网页、飞书、Slack）首次唤起、渲染进程忙、页面刚加载、窗口后台恢复时。
- **修法（后台串行队列 + 超时 + 强制 Chromium 建树 + 可观测）**：
  ```swift
  final class AXProbe {
      static let queue = DispatchQueue(label: "dev.focusvoice.ax", qos: .userInitiated)
      private static var prepared = Set<pid_t>()

      /// Chromium/Electron：提前打开 accessibility，避免首次查询卡死
      static func warmUp(pid: pid_t) {
          guard !prepared.contains(pid) else { return }
          prepared.insert(pid)
          let app = AXUIElementCreateApplication(pid)
          AXUIElementSetMessagingTimeout(app, 0.15)
          _ = AXUIElementSetAttributeValue(app, "AXManualAccessibility" as CFString, kCFBooleanTrue)
      }

      static func hitTest(_ point: CGPoint, completion: @escaping (AXUIElement?, AXError) -> Void) {
          queue.async {
              let system = AXUIElementCreateSystemWide()
              AXUIElementSetMessagingTimeout(system, 0.15)
              var el: AXUIElement?
              let cg = CGPoint(x: point.x,
                               y: CGDisplayBounds(CGMainDisplayID()).height - point.y)
              let err = AXUIElementCopyElementAtPosition(system, Float(cg.x), Float(cg.y), &el)
              DispatchQueue.main.async { completion(err == .success ? el : nil, err) }
          }
      }
  }
  ```
  `checkHold` 改为：先在后台命中，回主线程后再开 1.2s 判定窗口内的兜底；同时把失败原因写进 `lastTriggerFailure`，由菜单/一次性 HUD 展示（见 P0-3）。
- **验收**：在 Electron 应用里首次长按，日志应显示命中耗时；`AXError` 非 0 时 HUD 出现一次"未识别到输入框（AX 超时）"，不再静默。

### P0-3 触发失败 100% 静默：五处裸 return，无可观测性

- **位置**：1801（disabled）、1802（HUD）、1803-1804（屏幕）、1824（位移）、1828（AX 命中）、1829（InputDetector）。另有 1968/1978（session 不匹配）与 1939（busy/recording）。
- **现象**：用户唯一能说的是"没反应"；开发者/用户都无法自证是权限、AX、阈值还是判定问题。
- **根因**：没有统一失败原因枚举、没有日志、没有 HUD 提示、菜单栏也不变色（`updateStatus` 3230-3239 只处理 AX 权限文本，且只在打开菜单时可见）。

  菜单加一项「最近一次触发诊断」，显示 `AXIsProcessTrusted()`、`AXError`、命中 pid/role、移动距离。
- **验收**：人为吊销辅助功能权限后长按，菜单能显示"辅助功能权限未授权"，HUD 有提示。

### P0-4 InputDetector 黑名单顺序 + 42pt 几何排除 → 合法输入框被误杀

- **位置**：345（黑名单）、350（isEditable）、398-402（42pt 标题栏）、405-408（4pt 内缩）、410-413（内容区全放行）、1803-1804（visibleFrame）。
- **代码**：
  ```swift
  if ["AXScrollBar", "AXScrollThumb", "AXToolbar", "AXTitleBar", ...].contains(role) {
      return false                                   // 345：黑名单先于可编辑判断
  }
  if AX.isEditable(hit) { return true }              // 350
  ...
  let titlebarRect = CGRect(x: winFrame.minX, y: winFrame.minY, width: winFrame.width, height: 42.0)
  if titlebarRect.contains(cgPoint) { return false } // 398-402
  let innerContent = winFrame.insetBy(dx: 4, dy: 4)
  if !innerContent.contains(cgPoint) { return false }// 405-408
  return true                                        // 410-413 内容区任意点放行
  ```
- **现象 / 条件**：
  - 浏览器**地址栏 / 工具栏搜索框**：它们是 `AXTextField`，但 `role` 祖先/自身常是 `AXToolbar`，345 先判死，永远无法在地址栏听写。
  - **42pt 标题栏**：Chrome 的 tab+omnibox 高约 88pt，Codex/ChatGPT 桌面版自绘标题栏约 44-70pt；全屏窗口内容从 y=0 开始，顶部 42pt 全是正文。点击这些区域一律判死。
  - **贴边输入框**（聊天窗口底部输入框距底边 <4pt、侧边栏搜索框距边 <4pt）：405-408 误杀。
  - **全屏应用顶部条带**：1803-1804 用 `visibleFrame`（静态扣掉菜单栏），全屏应用顶部约 25pt 永远被拒。
  - 反过来：410-413 让**窗口内容区任意位置**都算输入目标 → 长按正文/消息列表/视频也起录音，随后在 2071-2076 丢掉整段录音，或把文字粘到别处（见 P0-6）。
- **修法**：
  1. 把 `AX.isEditable(hit)` **放在角色黑名单之前**；黑名单只排除"确定不可编辑"的元素。
  2. 删除几何 42pt 规则，改为**正向证据**：hit 或祖先链上出现 `AXTitleBar`/`AXToolbar` **且** 不可编辑时才排除；窗口拖拽区通常命中 `AXWindow`/`AXGroup` 且无 `AXSelectedTextRange`，天然被排除。
  3. 删除 4pt 内缩（或缩小到 1pt）。
  4. 屏幕守卫改用 `screen.frame.contains(point)`（只判断"是否在真实显示器上"），不要用 `visibleFrame`。
  5. 返回三态而不是 Bool（给 Controller 决定"忽略/提示/触发"）：
  ```swift
  enum Landing { case editable(AXUIElement); case uncertain(AXUIElement); case notText }

  static func landing(at p: CGPoint, hit: AXUIElement) -> Landing {
      if AX.isEditable(hit) { return .editable(hit) }
      // 祖先链最多 8 层，只查 role / 可写性，不再 30 层全量查询
      var cur: AXUIElement? = hit
      for _ in 0..<8 {
          guard let c = cur, let parent = AX.element(AX.value(c, kAXParentAttribute)) else { break }
          let role = AX.string(parent, kAXRoleAttribute) ?? ""
          if ["AXTextField", "AXTextArea", "AXSearchField", "AXComboBox"].contains(role) { return .editable(parent) }
          if role == "AXWindow" { break }
          cur = parent
      }
      return .uncertain(hit)
  }
  ```
  6. `isEditable` 增强（271-298）：
  ```swift
  static func isEditable(_ e: AXUIElement) -> Bool {
      if string(e, kAXSubroleAttribute) == "AXSecureTextField" { return false }
      if bool(e, kAXEnabledAttribute) == false { return false }
      let role = string(e, kAXRoleAttribute) ?? ""
      if ["AXTextField", "AXTextArea", "AXSearchField", "AXComboBox"].contains(role) { return true }
      // Chromium contenteditable / 富文本：没有 AXEditable 但有可写 value + 选区
      if AXUIElementIsAttributeSettable(e, kAXValueAttribute as CFString, nil) { return true }
      if value(e, kAXSelectedTextRangeAttribute) != nil { return true }
      if bool(e, "AXEditable") == true { return true }
      return false
  }
  ```
- **验收**：Chrome 地址栏、Safari 搜索框、全屏浏览器顶部输入、微信底部输入框、Codex 输入框均可触发；长按网页正文/消息列表不再触发。

### P0-5 会话状态竞态：`busy` 入口未置位 + 旧 Task 取消新录音

- **位置**：`start` 1938-1939（guard 但不置 busy）、1978-1981（stale 时 `recorder.cancel()`）、`finish` 2079、`cancel` 2144-2157。
- **代码**：
  ```swift
  func start(at point: CGPoint) {
      guard !recording, !busy else { return }         // 1939：此时 busy 仍为 false
      ...
      Task { @MainActor in
          ...
          try await self.recorder.start(source: source)   // 1977（唯一 recorder）
          guard self.sessionID == id else {
              self.recorder.cancel()                      // 1979-1980 ← 可能把新录音停掉
              return
          }
  ```
- **条件**：第一次长按后进入 `.preparing`（首次麦克风授权弹窗、`AVCaptureSession.startRunning` 100-500ms）；用户在这段时间内再次长按（因为没看到反应，非常自然）。第二次 `start` 通过 1939 的 guard（`busy` 为 false），产生新 sessionID；旧 Task 拿到授权后发现自己过期，调用 `recorder.cancel()`，而 `recorder` 是共享单例，**取消的是新会话正在使用的 AVCaptureSession**。
- **现象**：HUD 显示正在录音，但录到的是空/极短音频；finish 后"没有识别到语音"或"录音太短"。
- **修法**：把 4 个布尔 + UUID 改成显式状态机，且 `busy` 在入口同步置位；stale 分支不得操作共享 recorder：
  ```swift
  enum Phase: Equatable {
      case idle
      case preparing(UUID)
      case recording(UUID)
      case transcribing(UUID)
      case previewing(UUID)
  }
  private(set) var phase: Phase = .idle

  var busy: Bool {
      switch phase { case .idle: return false; default: return true }
  }

  func start(at point: CGPoint) {
      guard phase == .idle else { return }             // 唯一入口守卫
      let id = UUID()
      phase = .preparing(id)
      ...
      Task { @MainActor in
          ...
          try await self.recorder.start(source: source)
          guard self.phase == .preparing(id) else {
              // 只清理"本会话自己启动的"实例；更稳妥：每次 start 新建一个 UnifiedRecorder
              return
          }
          self.phase = .recording(id)
  ```
  最稳妥：`Controller` 每次会话**新建一个 `UnifiedRecorder`**，旧实例随会话丢弃，物理上不可能互相取消。
- **验收**：在授权弹窗出现期间连点长按 3 次，最终只有一次会话、录音时长正常。

- **代码**：

- **条件**：① 在网页正文/聊天记录区（被 410-413 放行）长按，当前焦点仍在底部输入框 → 录音后文字进输入框（用户以为"点了别的地方也录音"）；② 焦点输入框属于另一个 App/窗口（多窗口、点击未激活窗口、非激活面板）→ 文字进错误位置；③ 没有任何可编辑焦点 → 整段录音被删除，用户白说。

### P0-7 注入三路并发 + 不校验结果 → 重复粘贴 / 文本丢失 / 粘到错误 App

- **位置**：`TextInsertion.insert()` 1410-1455。
- **代码**：
  ```swift
  func insert(_ text: String, restoreClipboard: Bool) throws {     // 1410 参数未使用
      ...
      clipboard.clearContents(); clipboard.setString(text, forType: .string)  // 1415-1417 永久覆盖
      app.activate(options: [.activateIgnoringOtherApps])                     // 1420
      if let element = element {
          AXUIElementSetAttributeValue(element, kAXFocusedAttribute as CFString, kCFBooleanTrue)  // 1422
          if AX.isEditable(element) {
              let err = AXUIElementSetAttributeValue(element, kAXSelectedTextAttribute as CFString, text as CFTypeRef)
              if err == .success { return }          // 1424-1427 ← 不校验是否真的写入
          }
      }
      DispatchQueue.main.asyncAfter(deadline: .now() + 0.12) {
          ...
          down.postToPid(app.processIdentifier)      // 1441
          up.postToPid(app.processIdentifier)        // 1443
          down.post(tap: .cgSessionEventTap)         // 1445
          up.post(tap: .cgSessionEventTap)           // 1447
          DispatchQueue.main.asyncAfter(deadline: .now() + 0.15) {
              NSAppleScript(source: "tell application \"System Events\" to keystroke \"v\" using command down")?.executeAndReturnError(nil)  // 1451-1452
          }
      }
  }
  ```
- **现象**：一次听写插入 2-3 遍；或 HUD 显示"已插入文字"但输入框没字；或文字出现在另一个 App（终端/编辑器）里。
- **根因**：
  1. **三路粘贴无条件全发**：`postToPid`（进程级）+ `cgSessionEventTap`（会话级，落在当时前台窗口）+ 0.15s 后 System Events `keystroke`（落在当时前台 App）。当 AX 快速路径失败时三路都可能成功 → 重复；当前台切换未完成时，会话级/AppleScript 会粘到错误 App。
  2. **AX 不校验**：部分 CEF/Electron 对 `kAXSelectedText` 写入返回 `.success` 但不落地 → 直接 `return`，文本丢失，HUD 仍报"已插入文字"（1597-1600、2133、2189-2195）。
  3. **选区覆盖**：`kAXSelectedText` 是"替换当前选区"。双击选词、全选、或在录音前有选区时，长按触发后写入会**覆盖原文**（用户感知"丢字/句子被吃掉"）。未读取/保存 `kAXSelectedTextRange`，未区分折叠选区。
  4. **未等激活完成**：1420 → 1432 只有 120ms，`activate` 是异步的，`postToPid` 与 session tap 的目标可能不一致。
  5. **主线程阻塞**：1432-1453 的 `usleep`×3 + `NSAppleScript` 同步执行在主线程，卡 100-300ms（见 P0-1）。
  6. **剪贴板**：1415-1417 无条件覆盖；`restoreClipboard` 参数从未使用；设置项 `keepClipboard`（150-152/2540）是死代码，README 声称的恢复行为不存在。
- **修法（单路径 + 验证 + 等待激活）**：
  ```swift
  struct Injector {
      enum Outcome { case axOK, pasted, failed(String) }

      static func insert(_ text: String, into element: AXUIElement?, app: NSRunningApplication,
                         restoreClipboard: Bool) throws -> Outcome {
          guard AXIsProcessTrusted() else { throw FVError.message("需要辅助功能权限") }
          let pb = NSPasteboard.general
          let snapshot = restoreClipboard ? pb.pasteboardItems : nil
          let before = valueLength(element)

          // 1) 只走 AX 快路径，并读回校验；同时保留"在 caret 处插入"语义
          if let el = element, AX.isEditable(el) {
              // 若存在非折叠选区，先把光标收到选区末尾再插入，避免覆盖原文
              if let range = selectedRange(el), range.length > 0 {
                  var caret = CFRange(location: range.location + range.length, length: 0)
                  if let v = AXValueCreate(.cfRange, &caret) {
                      AXUIElementSetAttributeValue(el, kAXSelectedTextRangeAttribute as CFString, v)
                  }
              }
              AXUIElementSetAttributeValue(el, kAXFocusedAttribute as CFString, kCFBooleanTrue)
              let err = AXUIElementSetAttributeValue(el, kAXSelectedTextAttribute as CFString, text as CFTypeRef)
              if err == .success, waitUntil(0.25, { valueLength(element) != before }) {
                  return .axOK
              }
          }

          // 2) 等待目标 App 真正成为前台，再只发一路 ⌘V（pid 定向）
          activateAndWait(app, timeout: 0.8)
          pb.clearContents(); pb.setString(text, forType: .string)
          postCommandV(to: app.processIdentifier)                 // 只发这一路，不发 session tap
          guard waitUntil(0.7, { valueLength(element) != before }) else {
              return .failed("系统拒绝了模拟粘贴（可能是安全输入）")
          }
          if let snapshot { pb.clearContents(); pb.writeObjects(snapshot) }
          return .pasted
      }
  }
  ```
  另加：`IsSecureEventInputEnabled()` 时直接提示"当前应用启用了安全输入，已复制到剪贴板，请按 ⌘V"，不要假装成功。
- **验收**：Chrome / 微信 / TextEdit / Codex 各测 10 次：插入次数恰好 1 次；有选区时不丢原文；失败时 HUD 明确报错。

### P0-8 实时流 PCM 回调从未触发：`int16ChannelData` 恒为 nil（已实测）

- **位置**：`BuiltInMicRecorder.captureOutput` 496-522（尤其 517）；`SystemAudioRecorder.stream` 613-638（尤其 634）。
- **代码**：
  ```swift
  self.audioFile = try AVAudioFile(forWriting: fileURL, settings: settings)  // settings: 16k/mono/int16 (432-440)
  ...
  let out = AVAudioPCMBuffer(pcmFormat: file.processingFormat, frameCapacity: capacity)  // 502 / 619
  ...
  try? file.write(from: out)
  if let onChunk = self.onPCMChunk, let channel = out.int16ChannelData {  // 517 / 634
      let data = Data(bytes: channel[0], count: Int(out.frameLength) * MemoryLayout<Int16>.size)
      onChunk(data)
  }
  ```
- **实测证据**（本机 Swift 6.3.3，脚本 `/tmp/fv-audit/check_av.swift`）：
  ```
  processingFormat: <AVAudioFormat 0x...:  1 ch,  16000 Hz, Float32>
  commonFormat: 1 isInterleaved: false sampleRate: 16000.0 channels: 1
  int16ChannelData nil? true
  floatChannelData nil? false
  ```
  `AVAudioFile(forWriting:settings:)` 的 `processingFormat` 是 **Float32 解交织标准格式**，与写入文件用的 16-bit 设置无关。因此 `out.int16ChannelData` 恒为 nil，`onPCMChunk` **永远不会被调用**。
- **后果**：`UnifiedRecorder.beginSegment` 715-717/726-728 的桥接永不上报；`Controller` 2007-2009 的 `recorder.onPCMData` 永不触发；`TencentStreamRecognizer.sendPCMChunk` 一帧都没发出。HUD "实时: ..." 永远空白；`finish()` 2095 拿到空字符串后回退批式识别 → 用户仍需等 2-3 秒。
- **修法**：单独建 **16k/16-bit/单声道 interleaved** 目标格式，转换后用 `int16ChannelData`；或直接读 float 并手动量化。推荐前者（避免二次转换）：
  ```swift
  private let wireFormat = AVAudioFormat(commonFormat: .pcmFormatInt16,
                                         sampleRate: 16000,
                                         channels: 1,
                                         interleaved: true)!
  private var wireConverter: AVAudioConverter?

  // captureOutput 内：
  if wireConverter == nil || wireConverter?.inputFormat != srcFormat {
      wireConverter = AVAudioConverter(from: srcFormat, to: wireFormat)
  }
  let ratio = 16000.0 / srcFormat.sampleRate
  let cap = AVAudioFrameCount(ceil(Double(buf.frameLength) * ratio)) + 64
  guard let wire = AVAudioPCMBuffer(pcmFormat: wireFormat, frameCapacity: cap) else { return }
  var fed = false; var convErr: NSError?
  wireConverter?.convert(to: wire, error: &convErr) { _, status in
      if fed { status.pointee = .noDataNow; return nil }
      fed = true; status.pointee = .haveData; return buf
  }
  if convErr == nil, wire.frameLength > 0, let ch = wire.int16ChannelData {
      self.onPCMChunk?(Data(bytes: ch[0], count: Int(wire.frameLength) * MemoryLayout<Int16>.size))
  }
  ```
- **验收**：发送端日志统计每会话字节数（16k×2×秒数），应在 ±5% 内；HUD 实时字幕出现文字。
- **同类缺陷**：`capacity = frames * ratio + 64` 只是"够用"而不是"保平"；`AVAudioConverter` 单次喂入后剩余输入帧被丢弃，48k→16k 每 10.7ms 丢 1-2 帧，长录音累计漂移/吞字（见 P1-8）。

### P0-9 腾讯云实时流：句子覆盖丢字 + 签名未编码 + 默认引擎名在实时接口不合法

> 协议事实均对照腾讯云官方《实时语音识别（WebSocket）》文档：<https://cloud.tencent.com/document/product/1093/48982>（本次审计实时抓取原文核对）。

**(a) `voice_text_str` 是"当前一段话"结果，879 行直接覆盖 → 前几句全丢**

- 官方原文（Result 结构体）：`voice_text_str String 当前一段话文本结果`；`index Integer 当前一段话结果在整个音频流中的序号，从0开始逐句递增`。
- 代码 878-881：
  ```swift
  if let piece = resp.result?.voice_text_str, !piece.isEmpty {
      self.accumulatedText = piece        // 879 ← 覆盖，而不是按句子序号累积
      self.onLiveText?(piece)
  }
  ```
- **条件**：默认 `needvad = "1"`（909）→ 服务端按人声切句；用户说话中间停顿（极常见）→ 返回新句子 `voice_text_str` 只含新句；879 把前一句覆盖掉。
- **现象**：实时字幕只剩最后一句；最终插入文本只有最后一句（"丢字"）。多句听写尤其明显。
- **修法（用 `index` 累积，最终按序拼接）**：
  ```swift
  struct WSResp: Decodable {
      let code: Int?
      let message: String?
      let final: Int?
      struct Res: Decodable {
          let slice_type: Int?
          let index: Int?               // ← 新增
          let voice_text_str: String?
      }
      let result: Res?
  }
  private var sentences: [Int: String] = [:]
  private var maxIndex = -1

  if let res = resp.result, let piece = res.voice_text_str, !piece.isEmpty {
      let idx = res.index ?? 0
      sentences[idx] = piece
      maxIndex = max(maxIndex, idx)
      let merged = (0...maxIndex).compactMap { sentences[$0] }.joined()
      accumulatedText = merged
      onLiveText?(merged)
  }
  ```
- **验收**：连续说 3 句、句间停顿 1s，HUD 与最终插入都应包含 3 句。

**(b) 签名没有做严格 URL 编码 → 鉴权偶发失败**

- 官方原文："将 signature 值进行 urlencode（必须进行 URL 编码，编码函数必须要支持对 `+`、`=` 等特殊字符的编码，否则将导致鉴权失败偶发）"。
- 代码 925-928：
  ```swift
  guard let encodedSig = signature.addingPercentEncoding(withAllowedCharacters: .urlQueryAllowed) else { return nil }
  let fullURLString = "wss://\(host)\(path)?\(queryString)&signature=\(encodedSig)"
  ```
  `.urlQueryAllowed` **允许** `+`、`/`、`=`；Base64 的 `+` 会在服务端 query 解码时变成空格，`=` 也可能截断值 → HMAC 校验失败。约 1/3 的签名含 `+`。
- **现象**：实时流时好时坏；失败时 1996-1998 只 `NSLog`，用户无感知，最终静默回退批式（慢 2-3 秒）。
- **修法**：
  ```swift
  let unreserved = CharacterSet(charactersIn:
      "ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789-._~")
  guard let encodedSig = signature.addingPercentEncoding(withAllowedCharacters: unreserved) else { return nil }
  ```
  `queryString` 的每个 value 也应同样编码后再参与签名（当前值均为 ASCII 安全，仍建议统一）。

**(c) 默认引擎 `16k_zh_large` 不在实时接口支持列表 → 握手必失败**

- `Preferences` 170：`tencentEngineType = "16k_zh_large"`；设置页 2762-2767 也把 `16k_zh_large` 作为"推荐"项。
- 但官方实时 WebSocket 文档的 `engine_model_type` 列表中：大模型 1.0 为 `8k_zh_large`、`16k_zh_en`、`16k_multi_lang`、`16k_en_large`；通用为 `16k_zh`、`16k_zh-TW`、`16k_yue`、`16k_en`…，**没有 `16k_zh_large`**（`16k_zh_large` 是批式 `SentenceRecognition` 的引擎名）。
- **后果**：`sr.start()`（2000-2005）能建连（`isConnected = true` 在 788 行握手前就置位），但服务端随后返回非 0 `code`；`handleIncomingJSON` 873-876 只 `onError`，HUD 不知情；`finish()` 等 1.5s 拿空字符串 → 回退批式。**"实时流"实际从未工作，用户仍在等 2-3 秒，且以为是自己网络问题。**
- **修法**：实时引擎做映射（中文场景 `16k_zh_en` 或 `16k_zh`），设置页只展示实时接口真正支持的引擎；`start()` 后等待握手 `code == 0` 再置 `isConnected/ready`；握手失败在 HUD 明确提示并自动切到批式（提示原因）。
- **验收**：用真实密钥跑一次，日志应出现 `code: 0 / message: success` 的握手响应；HUD 实时字幕滚动。

**(d) 其他实时流缺陷**（P1/P2 详列）
- `start()` 788 在握手前置 `isConnected = true`，握手失败也可能先发音频。
- `finish()` 815-821 硬等 1.5s，长音频/服务端排队时截断最后一句；应在收到 `final == 1` 或 `code != 0` 时立即返回，最长 5s，并保留已累积句子。
- 发送粒度：官方建议 16k 每 200ms 发 6400 字节；当前每个音频回调（约 10ms/320B）发一帧，100 帧/秒，服务端压力与重传放大（P2）。
- 无心跳/重连；`sendPCMChunk` 796 出错只 NSLog；`engine` 改变不重连（下次录音重建，可接受）。
- 1990 只校验 `appId`/`secretId` 非空，未校验 `secretKey`；空 key 时签名必然失败且无提示。

### P0-10 无总超时：`busy` 可永久卡死，全局长按从此"没反应"

- **位置**：`Recognizer.apple` 1126-1135（`withCheckedThrowingContinuation` 无超时）；`Recognizer.whisperViaCLI` 1173-1178（`waitUntilExit` 无超时）；`finish` 2079-2141（`busy` 只能靠 Task 结束复位）。
- **代码**：
  ```swift
  _ = recognizer.recognitionTask(with: request) { result, error in
      ... if let result = result, result.isFinal { c.resume(...) }     // 1129-1134 永不 final 就不 resume
  }
  ...
  let status: Int32 = await withCheckedContinuation { c in
      DispatchQueue.global(qos: .userInitiated).async {
          task.waitUntilExit()                                        // 1175 无限等待
          c.resume(returning: task.terminationStatus)
      }
  }
  ```
- **条件**：`SFSpeechURLRecognitionRequest` 偶发不回调 final；whisper-cli 因模型损坏/Metal/端口冲突挂起；`WhisperServer.request` 若服务端接受连接但不返回（180s 后抛，仍可接受但过长）。
- **现象**：HUD 停"正在转录…"（无取消按钮，Esc 在 2049 已被移除），`busy` 永久 true；之后所有长按/⌥Space 在 1939 静默 return，**整个 app 只剩菜单还活着**。
- **修法**：所有识别路径加统一超时；超时后必须 `task.terminate()`（CLI）与 `recognitionTask.cancel()`（Apple），并复位状态：
  ```swift
  func withTimeout<T>(_ seconds: TimeInterval, _ op: @escaping () async throws -> T) async throws -> T {
      try await withThrowingTaskGroup(of: T.self) { group in
          group.addTask { try await op() }
          group.addTask {
              try await Task.sleep(for: .seconds(seconds))
              throw FVError.message("识别超时（\(Int(seconds))s）")
          }
          defer { group.cancelAll() }
          guard let first = try await group.next() else { throw FVError.message("识别失败") }
          return first
      }
  }
  // CLI：
  let watchdog = DispatchWorkItem { if task.isRunning { task.terminate() } }
  DispatchQueue.global().asyncAfter(deadline: .now() + 120, execute: watchdog)
  // Apple：
  let timeoutTask = Task { try? await Task.sleep(for: .seconds(20)); task.cancel() }
  ```
  并且 `phase` 状态机保证任何异常都回到 `.idle`（P0-5 的重构天然解决）。
- **验收**：人为把模型路径指向一个会挂起的脚本，20s 后 HUD 报错、`busy` 复位、下一次长按正常。

### P0-12 切换录音来源失败 → 后续整段录音静默丢失

- **位置**：`UnifiedRecorder.switchSource` 660-666；`beginSegment` 709-733；`finishActiveRecorder` 735-740；`UnifiedRecorder.stop` 668-701。
- **代码**：
  ```swift

      finishActiveRecorder()                       // 710 ← 先把当前来源停掉
      ...
      case .system:
          guard CGPreflightScreenCaptureAccess() else {
              CGRequestScreenCaptureAccess()
              throw FVError.message("内录需要“屏幕录制”权限，请在系统设置中允许后重试")   // 721-724

  ```

  ```swift
  func switchSource() async throws -> AudioSource {

          throw FVError.message("内录需要屏幕录制权限；已保持当前麦克风录音")

      let newURL = tempURL()
      let newRecorder = try await makeRecorder(next, to: newURL)   // 先起新
      segments.append(newURL)
      let old = activeRecorder
      activeRecorder = newRecorder
      currentSource = next
      old?.stop()                                                  // 后停旧
      return next
  }
  ```
  并给 `SCStream` 加 `delegate`（见 P1-9），失败时通过回调报错。
- **验收**：未授权屏幕录制时点切换 → HUD 报错且麦克风录音不中断；授权后切换，前后内容都在。

### P1-8 采样率转换丢帧/漂移（吞字）

### P1-11 录音停止时尾部音频被丢弃（尾字丢失）

### P1-14 `WhisperServer` 端口随机、无冲突重试、进程泄漏

- 位置：989（随机端口）、1029-1039（20s 超时即失败）、1007-1014（zsh 包装进程）、969-979（`terminate()` 不等退出）。
- 风险：端口被占用 → 20s 后失败；App 崩溃/强退后 zsh 子进程与 `whisper-server` 可能残留（占 2.9GB 内存）；重启时短暂两个 server。
- 修法：绑定 0 端口让系统分配不可行（server 需显式端口）→ 用 `bind` 探针找空闲端口 + 失败换端口重试 3 次；用 `setpgid`/`kill(-pgid, SIGTERM)` 杀进程组；启动时写 PID 文件，下次启动清理残留；`terminate` 后 `waitUntilExit` 带超时。
- 验收：占用 20000-39999 中多个端口仍能启动；强退后无残留进程。

### P1-15 `recognize`/`finish` 在主线程做重 IO 与 base64

- 位置：1059（`Data(contentsOf: file)` 构 multipart）、1229-1245（读 WAV + base64 + JSON）、1233（`base64EncodedString()`）、1381（JSON 解析）。
- 现象：长录音（30-60s）时主线程卡 20-80ms；与 P0-1 联动。
- 修法：`Recognizer` 改成 `nonisolated`/后台执行，`URLSession` 上传用 `upload(for:fromFile:)` 避免整段进内存；base64 在后台队列；`Preferences` 的读取回主线程。

### P1-16 腾讯批式识别无时长校验（>60s 必失败）

- 位置：1216-1311（`SentenceRecognition` 直接传整段 WAV）；录音上限 300s（2220-2227）。
- 事实：官方 SentenceRecognition 单次音频 ≤60s（文档 `DataLen` 限制），当前代码无切分。
- 现象：用户录 1-2 分钟，腾讯引擎必然报错；whisper 则要处理超长音频（慢）。
- 修法：>55s 自动切段（WAV 头解析 + PCM 分片）分别识别再拼接；或直接禁用批式腾讯引擎并引导实时流。
- 验收：录 90s 腾讯引擎能返回完整文本。

### P1-17 预览窗抢焦点，插入目标易失效

- 位置：2261-2368（`PreviewController.present`）、2358（`NSApp.activate`）、2360（`makeFirstResponder`）。
- 现象：预览期间 FocusVoice 成为前台 App；点击"插入"时目标 App 处于后台，`app.activate` 异步未完成就发粘贴（P0-7），AX element 可能已失效。
- 修法：预览窗保持 `nonactivatingPanel` 且不 `NSApp.activate`（仅 `makeKeyAndOrderFront` 可能不够，需要 `orderFrontRegardless` + `makeFirstResponder`）；或插入时等待目标 App 激活完成；预览面板 `isMovableByWindowBackground` 已有，保持。
- 验收：预览→插入 10 次全部命中原输入框。

### P1-18 关闭历史/失败无恢复路径

- 位置：2064-2076（太短/无目标直接删音频）、2189-2195（成功才进历史）。
- 修法：失败音频保留 24h 并在菜单提供"重新转写/播放"；历史持久化（UserDefaults/JSON），失败原因记录。

### P1-19 权限失效无自愈与提示

- 位置：3147-3219（启动时请求一次 AX 权限）、3230-3239（每 1.5s 只改菜单文字）、1793（`setEnabled` 死代码）。
- 现象：重装/换路径/签名变化导致 TCC 失效时，长按完全无反应，菜单栏仍是"◉"。
- 修法：启动与每 5s 检测 `AXIsProcessTrusted()`，失败时状态栏图标变橙 + 一次性 HUD 提示"辅助功能权限已失效，点此打开设置"；恢复后自动重建监听（监听本身无需重建，但可重新 warmUp AX）。
- 验收：吊销权限后 5s 内有可见提示。

### P1-20 `Hotkey.install()` 失败静默

- 位置：3223（`_ = hotkey.install()`）、1872-1880。
- 现象：⌥Space 被占用/注册失败时，备用触发完全不可用；且 ⌥Space 在文本框中会输入不换行空格（NBSP），用户可能以为"出现乱码"。
- 修法：检查返回值，失败时菜单显示"快捷键不可用（被占用）"，提供自定义快捷键设置；注册成功后用本地监听屏蔽 NBSP。

## 6. 关于用户痛点②（"边录边看实时文字"）的落地方案

当前代码里"实时"只有腾讯一条路，而它被 P0-8/P0-9 三重打断；whisper 是"录完再转"，没有任何部分结果。建议分两层：

1. **保留腾讯实时**：按 Top 5 修好即可获得真流式（中文推荐 `16k_zh_en` 或 `16k_zh`；`needvad=1` 保留，但必须按 `index` 累积）。
2. **whisper 场景的"伪实时"**：录的同时起一个轻量端侧流式预览，最终文本仍用 large-v3：
   ```swift
   // 预览引擎：Apple 端侧识别（SFSpeechRecognizer，支持 partial result）
   final class LivePreview {
       private var recognizer: SFSpeechRecognizer?
       private var request: SFSpeechAudioBufferRecognitionRequest?
       private var task: SFSpeechRecognitionTask?
       var onPartial: ((String) -> Void)?

       func start(locale: String = "zh-CN") async throws {
           let auth = await withCheckedContinuation {
               SFSpeechRecognizer.requestAuthorization { $0.resume(returning: $0) }
           } as SFSpeechRecognizerAuthorizationStatus
           guard auth == .authorized else { throw FVError.message("预览需要语音识别权限") }
           guard let r = SFSpeechRecognizer(locale: Locale(identifier: locale)),
                 r.supportsOnDeviceRecognition else { throw FVError.message("端侧预览不可用") }
           recognizer = r
           let req = SFSpeechAudioBufferRecognitionRequest()
           req.shouldReportPartialResults = true
           req.requiresOnDeviceRecognition = true
           request = req
           task = r.recognitionTask(with: req) { [weak self] result, _ in
               if let t = result?.bestTranscription.formattedString { self?.onPartial?(t) }
           }
       }

       // UnifiedRecorder.onPCMData 的 16k/16-bit/mono PCM 直接转为 AVAudioPCMBuffer 喂入
       func append(_ pcm: Data) {
           guard let req = request,
                 let fmt = AVAudioFormat(commonFormat: .pcmFormatInt16, sampleRate: 16000,
                                         channels: 1, interleaved: true),
                 let buf = AVAudioPCMBuffer(pcmFormat: fmt,
                                            frameCapacity: AVAudioFrameCount(pcm.count / 2))
           else { return }
           buf.frameLength = AVAudioFrameCount(pcm.count / 2)
           pcm.withUnsafeBytes { raw in
               memcpy(buf.int16ChannelData![0], raw.baseAddress!, pcm.count)
           }
           req.append(buf)
       }

       func stop() { request?.endAudio(); task?.cancel(); task = nil; request = nil }
   }
   ```
   - 录音开始即启动预览（`onPCMData` 分发给腾讯和预览两路）；HUD 的 `setLiveTranscript` 已有（1618-1625）可直接显示。
   - `finish()` 时先 `stop()` 预览，再用 whisper 最终结果覆盖（避免预览错误留在正文）。
   - 预览引擎不可用（未授权/语言不支持）时静默降级，不阻塞主流程。
3. **更优解**：如果你正在集成的 sherpa-onnx SenseVoice（v0.8）支持真流式，直接用它做预览，large-v3 只做最终校正；架构与上面完全一致，把 `LivePreview` 换成 SenseVoice 即可。

## 7. 验证方法与证据

1. **`AVAudioFile` 格式实测**（P0-8）：
